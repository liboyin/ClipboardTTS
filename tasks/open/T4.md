# T4 — Three provider failures give a message that the user cannot act on

**Priority:** Non-blocking. Needs the user's decision on one trade-off. The provider behavior is documented or reported, and no live run confirmed it.

The source paths below were validated by inspection at `01e94f3` on 2026-11-17.

- **Gemini HTTP 400 and 429:** `userFacingHTTPError` in [the failure mapping](../../Sources/Managers/TTSNetworkManager+Failures.swift) relates only 401 and 403 to the key. Every other status reads "Speech request failed (HTTP N)."
- Google's [API errors reference](https://ai.google.dev/gemini-api/docs/generate-content/api-errors) shows an invalid key answered with HTTP 400 and the reason `API_KEY_INVALID`. It documents 429 as an exceeded rate limit or spend limit.
- **Realtime `response.done` with the status `failed`:** `classify` in [OpenAIRealtimeSpeech](../../Sources/Managers/OpenAIRealtimeSpeech.swift) reads only the status. It reports "The TTS service reported an error" and ignores `response.status_details.error`.
- Community reports show quota codes and rate-limit codes in that object. This is a hypothesis. The review found no official table, and DESIGN records only the `error` event observed on 2026-11-02.
- **Refused Realtime handshake:** A connection that fails before any frame reads "Couldn't reach the TTS service. Check your connection". The app never reads the HTTP status of the handshake.
- This is a hypothesis too. DESIGN records that a rejected key passes the handshake. The review does not know which statuses OpenAI answers a handshake with.
- **Expected outcome:** Each case names what the user can change: the key, the model and the voice, or the limits of the account. No message quotes provider text.
- **Trade-off for the user:** A mapping by status alone cannot tell a bad Gemini key from a bad voice, because both are 400. A bounded read of the error body can. The app drops error bodies unread today.
- **Validation:** One test for each mapping, and one for a status that keeps the generic message. A live check of a provider's answer needs the user's authorization.
- **Dependencies:** The user's decision on the trade-off. T3 (missing key) removes the most common cause of the first case and of the third case.
