# T3 — A request without a saved key still goes to OpenAI or Gemini

**Priority:** Non-blocking. Needs the user's acceptance, because the refusal is user-visible.

- **Evidence:** Validated by source inspection at `01e94f3` on 2026-11-17. `streamTTS` in [the request lifecycle](../../Sources/Managers/TTSNetworkManager+RequestLifecycle.swift) sends an empty key as it sends any other. It checks no key before it connects.
- A fresh install selects OpenAI with no key. The first click on Speak Copied Text therefore takes this path.
- **Hypothesis, not verified:** The review ran no live request, so it does not know what the user sees. A refused OpenAI handshake would read "Couldn't reach the TTS service", which blames the network.
- **Expected outcome:** With OpenAI or Gemini selected and no saved key, the request fails before any connection. The message names the provider and sends the user to Settings.
- Custom stays exempt. A local server such as Kokoro ignores the key, and README tells the user that an empty key works.
- **Implementation note:** `failRequestBeforeItStarts` already publishes a failure and ends the session for the other local refusals.
- **Validation:** Tests show that no HTTP task and no Realtime connection starts, and that the client receives one failed terminal event. A Custom request with an empty key still starts.
- **Dependencies:** None. T4 (provider failure messages) changes the same set of messages. If the user accepts both, bound them together.
