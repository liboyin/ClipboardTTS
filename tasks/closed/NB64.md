# NB64 — Three runner tool calls may not read their output as README describes

**Outcome:** Fixed: the mutation runner reads `uname` and both `git rev-parse` outputs as bytes and decodes them as UTF-8, so a checkout path outside ASCII works under a non-UTF-8 locale and a failed call's stderr gets U+FFFD replacement.

**Origin:** S11's independent verification on 2026-11-16 found that README said a byte that cannot be decoded in a failed tool's error output reads as U+FFFD. However, `run-mutants.py` ran `uname -m` (`:477`) and both `git rev-parse` calls (`:597`, `:621`) with `text=True`, so `subprocess` decoded their output strictly in the locale's encoding before `describe` saw it. It was recorded as a hypothesis in `7a4f3df`. The Codex commit `1e67285` then narrowed README to that behavior, pending this investigation. The user asked for NB64 to be carried out the same day.

## Accepted boundary

The boundary was kept in the task's working review record.

- **Intent:** the three calls capture bytes and decode them explicitly as UTF-8, like the runner's other Git calls. A repository path outside ASCII then resolves whatever the locale, and a failed call's stderr reaches `describe` as bytes, which replaces an undecodable byte with U+FFFD.
- **Compatibility surface:** the runner's command line, exit codes, `results.json`, and verdicts are unchanged; only how these three outputs are decoded changes.
- **Non-goals:** other decoding sites, which already decode bytes explicitly (`ls-files`, the spec, logs, mutated files); `verify-coverage-gate.py`; and S10's review of the tooling.
- **Validation and done:** a verifier case that runs the runner from a non-ASCII repository path under ISO 8859-1 and fails on the revert, with mutants run against it. Also the full verifier, the AGENTS gates, README describing the fixed behavior, review, and archival.

## Probe

Run at `1e67285` on macOS 27.2.1 arm64 with the system `python3`. The probe used two local clones in the session scratchpad, one under a directory named `probé` and one with an ASCII path. It ran the real runner with a spec whose edit text is absent, so every run that resolves the repository correctly refuses at planning, before any test run.

- Under `LANG`/`LC_ALL=en_US.ISO8859-1`, the non-ASCII clone refused with exit 2: `fatal: cannot change to '…/probÃ©/repo'`, from `git ls-files`. The repository root had been decoded as Latin-1 and named a directory that does not exist.
- Under `en_US.UTF-8`, and for the ASCII clone under either locale, the runner reached the expected refusal: `old text occurs 0 times in README.md`.
- The strict-decoding `UnicodeDecodeError` the hypothesis also named was not reached and is not reachable through these calls on macOS. Paths there are UTF-8, `uname -m` and `rev-parse HEAD` print ASCII, and ISO 8859-1 decodes every byte. Had it occurred, it is a `ValueError`: the setup handler would have refused with exit 2 for the Git calls, and the mutant loop would have raised for `uname`.

So the defect is real, but it is not the one first suspected: a non-ASCII checkout path cannot be used under a non-UTF-8 locale, which the verifier already exercises for test names.

## Implementation

**NB64 — Fixed.** The main agent made the change.

- `run-mutants.py`: `uname -m` and `rev-parse HEAD` read `.stdout.decode().strip()` from captured bytes. `rev-parse --show-toplevel` does the same, with a comment explaining why.
- `verify-mutation-runner.py`: new case `a_repository_path_outside_ascii_is_found_under_any_locale`. It builds the usual fixture under a directory named `dépôt` and runs the runner under ISO 8859-1, with `PYTHONUTF8=0` and strict ISO 8859-1 stdio, as the existing test-name locale case does. It asserts exit 0 with no traceback, the exact control and kill lines, and a complete `results.json` whose `head` matches the fixture.
- README's Mutation Testing section says that tool output the runner reads as text is captured as bytes and decoded as UTF-8 whatever the locale. A repository path outside ASCII is therefore found under any locale, and a failed tool's stderr gets U+FFFD replacement.

## Limitations

- Only macOS's own UTF-8 paths were exercised. A substituted tool printing non-UTF-8 text through these calls would now fail strict UTF-8 decoding instead of locale decoding; no supported tool does.
- The probe used ISO 8859-1 and UTF-8 only, the two locales the verifier exercises.
