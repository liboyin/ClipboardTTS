# NB55 — Dragging the position slider re-encodes the remaining buffer on the main thread

**Outcome:** Accepted without change. A measurement showed that a seek on long audio does not stall the optimized build.

**Non-blocking; structure Validated by source inspection, cost unmeasured — 2026-11-03 second review.** `Sources/Views/MenuBarView.swift:90` passes `AudioPlayerManager.seek(to:)` as the position `MenuSlider`'s `onEdit`, and the continuous `NSSlider` calls it on every drag event, as the SwiftUI slider it replaced in [B5](../closed/B5.md) did. `seek` (`Sources/Managers/AudioPlayerManager.swift:369`) runs inside `bufferQueue.sync` on the main queue and converts every remaining buffered frame into one new Float32 `AVAudioPCMBuffer` (`:404`–`:409`, `makePCMBuffer` at `:431`). The buffer keeps the whole session's PCM (`pcmData` is never trimmed), and only the clipboard OpenAI path is length-capped, so for a long Gemini, Custom, or Services read each drag event costs in proportion to the audio after the thumb: ten minutes at 24 kHz is 14.4 M frames, a 58 MB float allocation. No hitch was observed or measured. **Outcome:** decide from a measurement whether dragging long audio stalls the menu; if it does, bound the cost of a seek (for example, schedule the remainder in bounded chunks, or seek on drag end) while preserving exact-end seek/replay, clamping, and underrun release. **Validation:** first measure seek duration on a long owned buffer at HEAD; a change keeps the existing seek/replay tests and adds one that fails when a seek converts more than the bound. **Dependencies:** none; serialized frame counts, not published durations, keep deciding seek boundaries.

## Measurement — 2026-11-17

The task asks for a measurement at `HEAD` before any change. This section records it. No source changed.

**Baseline.** At `1c93aec` on macOS 27.2.1 (Apple M2), both gates passed. `./check-coverage.sh` ran 452 tests with 0 failures, and reported 97.85% for `Sources/Managers/` and 97.25% for the application logic. The Debug build with signing disabled succeeded, with 0 SwiftLint violations in 120 files. Its only warning was the AppIntents metadata warning that README calls benign.

**Method.** A diagnostic XCTest ran alone, with `-only-testing`, in a `git archive` scratch copy of `1c93aec`, into scratch derived data.

- The test built each player with `makeOwnedAudioPlayer`, and it buffered silence only, so nothing audible played and no developer state was touched.
- It timed seven `seek(to:)` calls on 1, 10 and 30 minutes of 24 kHz audio, first paused and then playing.
- It ran twice: as the ordinary Debug build, and with `SWIFT_OPTIMIZATION_LEVEL=-O`, which is the optimization of the Release build that `package.sh` ships.
- The test bundle does not compile in the Release configuration, because the tests use hooks that exist only under `DEBUG`. The optimized Debug build is therefore the nearest measurable stand-in for the shipped app.

**Result.** Each value is the time of one `seek` to the start of the buffer, in milliseconds. A seek to the start is the most expensive one.

| Buffered audio | Debug, paused | Debug, playing | Optimized, paused | Optimized, playing |
|---|---|---|---|---|
| 1 minute | 132–138 | 139–149 | 1.6–2.1 | 10.6–10.8 |
| 10 minutes | 1,343–1,357 | 1,344–1,376 | 13–16 | 21 |
| 30 minutes | 4,094–4,131 | 4,064–4,096 | 38–48 | 43–64 |

- The cost is proportional to the audio after the thumb, as the task predicted. A seek to 90% of 30 minutes took 5 ms paused and 11 ms playing in the optimized build.
- A playing seek never took less than about 10.6 ms, whatever the length. That floor comes from stopping and restarting the player node, not from the conversion.
- The unoptimized conversion loop is about 250 times slower than the optimized one. The seconds-long stall exists only in a Debug build.

**Limitations.**

- No one dragged the real slider. The table measures the call that each drag event makes, not the feel of the menu.
- The optimized Debug build is a stand-in. The Release app itself was not measured.
- The measurement ran on one Apple M2. Memory use was not measured. Each seek still allocates four bytes for each remaining frame, which is 173 MB at 30 minutes.

## Disposition

The task says to bound the cost only if dragging long audio stalls the menu. In the optimized build, one drag event blocks the main thread for about 21 ms at 10 minutes and for about 50 ms at 30 minutes.

- **Decision:** on 2026-11-17 the user accepted the finding without change, on the main agent's recommendation.
- **Reason:** the stall of seconds exists only in a Debug build. A change in the audio path costs much validation for a small gain.
- **Revisit trigger:** reads of more than about 20 minutes become common, or someone sees the thumb lag during a drag.
- **Alternatives not taken:** a seek only when the drag ends, which stops live scrubbing, and a bounded conversion, which touches the player's concurrency.

No source changed, so the gates, the mutation evidence and the formal review do not apply. The comment in `Sources/Views/MenuBarView.swift` that names NB55 stays, and it now points at this record.
