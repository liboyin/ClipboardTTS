# NB42 — A short-tool deadline no wait can represent is refused before anything runs

**Origin:** reported by [NB35](NB35.md)'s third review round on 2026-09-26 and recorded in TODO as not independently validated: `positive_seconds` accepted any finite positive number, but `run_shielded` passes the short-tool deadline to `communicate()`, which raised `OverflowError` for `--tool-deadline 1e308`, so the run ended with a traceback, exit 1, which README reserves for unjudged mutants, and a `results.json` recording an unexpected exception before the control. By user decision on 2026-09-26 it was to be fixed, and it was assigned the same day.

**Boundary:** refuse at argument parsing, with an `error:` diagnostic and exit 2 before any lock, copy, or tool, a `--tool-deadline` that `communicate()` cannot wait for, and keep accepting every deadline a wait can represent. NB41's `OSError` refusal, catching `OverflowError` at run time, the deadlines' defaults and mechanics, verdicts, exit codes, S3, S4, NB34, NB39, and NB40 were out of scope, and `--tool-deadline` stays a hidden verifier seam that README does not describe. Validation was verifier cases on both interpreters, mutation evidence against the unmodified verifier, AGENTS' gates, and the review skill's full procedure.

**Revalidation** at `bd15cde` on 2026-09-26, with the verifier's fixture and stand-in tools, identically on Python 3.13.9 and `/usr/bin/python3` 3.9.6. `--tool-deadline` `1e308`, `1e10`, and `2147484` each ended with an `OverflowError` traceback (`cannot convert float infinity to integer`, `timestamp too large to convert to C PyTime_t` (`_PyTime_t` on 3.9), and `timeout is too large`), exit 1, no test run, and a `results.json` with `complete: false`, `exit: 1`, `the runner raised an unexpected exception`, and no control; `2147483` ran to exit 0. `--test-deadline` `1e308` and `1.7976931348623157e308`, the largest finite float, both ran to exit 0.

**Measured bound.** On both interpreters `communicate()` waits through `PollSelector`, which rounds the time left up to whole milliseconds and passes it to `poll()`, whose timeout is a C `int`, so no wait longer than 2147483647 ms, 2147483.647 s or about 24.8 days, can be made. A direct probe of `communicate()` on a child that sleeps 50 ms accepted `2147483.647` and refused `2147483.648` on both interpreters; one bisection on each put the last accepted value 34 µs (3.13) and 95 µs (3.9) above 2147483.647 s, the time that passed before the first `poll()`. `Popen.wait()` with a timeout sleeps in steps of at most 50 ms and never converts the whole timeout, so it returned normally at the largest finite float on both, and `time.monotonic()` plus that value stays finite. The deadline reaches these sites: `communicate()` in `run_shielded` (the short-tool deadline; this is the only one that overflows), `process.wait` for the test run (the test-run deadline), `process.wait` for a stopped test tool (the short-tool deadline), and `kill_session`'s `ps` listings, whose `subprocess.run` timeout is what is left of the short-tool deadline and so never exceeds it.

**Change.** `run-mutants.py` gains `TOOL_DEADLINE_LIMIT = (2**31 - 1) // 1000`, 2147483 s, and `tool_seconds`, the `--tool-deadline` argparse type: it applies `positive_seconds` and refuses a larger value with `'<text>' is longer than the 2147483 seconds a short tool can be waited for`, which argparse prints after the usage as `run-mutants.py: error: argument --tool-deadline: …`, exiting 2 before `main` does anything else. The limit is whole seconds rather than the exact 2147483.647 s: at the exact limit, whether `poll()` accepts the rounded time left depends on how much time has passed and on how the sum with `time.monotonic()` rounded, whereas 2147483 s stays 647 ms below it. `--test-deadline` keeps `positive_seconds`, because the only wait it reaches can represent every finite value; bounding it would have refused deadlines that work.

**Verifier.** Two cases were added, and no existing case changed. `a_short_tool_deadline_no_wait_can_represent_is_refused` passes `--tool-deadline` `2147484`, `1e10`, and `1e308`, one per `OverflowError` path, and asserts exit 2, an `error:` diagnostic naming the option, no traceback, no test run, and no `--out` directory, which a check made after the lock would have created. `the_longest_deadlines_a_wait_can_represent_are_accepted` runs a campaign with `--tool-deadline 2147483` and `--test-deadline 1.7976931348623157e308` and asserts exit 0, no traceback, and both deadlines recorded in `results.json`; the stand-in XcodeGen and `uname` are waited for through `communicate()` at the limit, so the case also shows on whichever interpreter runs it that the limit is representable. `./verify-mutation-runner.py` passes 110/110 on Python 3.13.9 and on `/usr/bin/python3` 3.9.6; `bd15cde`'s runner fails exactly the refusal case (109/110), with the `OverflowError` traceback.

**Limitations.** The limit is `poll()`'s, measured on macOS with both interpreters' `PollSelector`; an interpreter whose `communicate()` waited another way could accept more or less, which the acceptance case would show at the limit but not above it. The 647 ms margin is a judgement that no case can observe: a value between 2147483 s and 2147483.647 s would work in practice but is refused. The test-run deadline stays unbounded because `Popen.wait()` is a sleep loop on both interpreters; a Python whose `wait()` converted its timeout could overflow there, which the acceptance case would catch.
