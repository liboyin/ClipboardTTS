# B4 — Progress ticks cannot interleave with seek

Moved from [TODO.md](../TODO.md) on 2026-09-24 without rewording; the text below is the disposition as TODO recorded it, and its evidence is tied to the revisions it names.

**B4 — Fixed.** `AudioPlayerManager.applyProgressTick()` reads the node's rendered position and publishes the position it implies in one main-queue turn, and the repeating timer does nothing but call it, so no rendered position is held across a turn in which `seek` can install a new `baseProgressOffset`. The tick keeps the clamp and the pause it performs on reaching the buffered end, and still publishes nothing when the node reports no rendered position. It is internal so its tests drive it as the timer does; the position it reads comes from an injected reader, and the manager builds its own repeating timer while an injected scheduler decides where that timer runs, because a test can otherwise neither state what live audio has rendered nor place a tick without waiting a cadence out. Reaching the buffered end paused through `pause()` at the time, so the tick also revoked the prebuffer start pending behind it; B2 later moved that stop onto a path that records why playback stopped, and it still performs the same revocation. Mutants that defer either the publication or the whole tick reproduce the 1.8-to-2.0 advance, and ones that drop the clamp, the missing-reading guard, the timer's call into the tick, its scheduling, its invalidation, its cadence, or that end the stream without `pause()`'s revocation each fail a test. README owns the current contract. B2 later gave the tick's stop at the buffered end a recorded reason, so that stop is now the entry point to the end-of-playback state machine rather than the end of playback itself.
