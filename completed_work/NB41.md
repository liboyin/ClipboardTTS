# NB41 — The runner's refusal of an OS error before the control is held

**Origin:** reported by [S2](S2.md)'s eleventh review on 2026-09-26 and recorded in TODO as not independently validated: `run-mutants.py` refuses an `OSError` raised before the control, such as a mistyped spec path or an `--out` that cannot be created, with `error:` and exit 2, but removing `OSError` from `main`'s first `except` survived the verifier, and a nonexistent spec path then ended with a traceback and exit 1, which README reserves for an unjudged mutant. The user authorized it on 2026-09-27 (D22) as the fourth task of the mutation runner's sequence, after [NB40](NB40.md).

**Boundary:** hold, with verifier cases, that an `OSError` raised before the control begins is refused as any other input is (an `error:` diagnostic naming its cause, exit 2, no traceback, no test run, and no `results.json`), and that the refusal stays that narrow, so an exception the runner does not expect before the control still propagates rather than reading as a refusal. The change was verifier-only, with a README clause; the runner stayed unchanged because revalidation found it already refused these inputs correctly. Any change to `run-mutants.py`, verdicts, exit codes, or diagnostics, the exit status an unexpected exception gives, an `OSError` once the control has begun (which existing cases hold), NB34, S4, and NB43 were out of scope. Validation was the cases on both interpreters, mutation evidence against the unmodified verifier, AGENTS' gates, and the review skill's full procedure.

**Revalidation** at `a7a0451` on 2026-09-28. With the runner (`b35844d1…`) and the 116-case verifier (`9992eb52…`) unchanged since NB40, the revert and seven further mutants below, all but the one wrapping only `claim_output`, which was added later, each passed the verifier 116/116 on Python 3.13.9. A probe, run identically on Python 3.13.9 and `/usr/bin/python3` 3.9.6, in the verifier's fixture ran `HEAD`'s runner with a missing spec, an unreadable spec (mode 000), a spec that is a directory, and an `--out` beneath a regular file: each exited 2 with a single line `error: [Errno 2] No such file or directory: '…/missing.json'`, `[Errno 13] Permission denied`, `[Errno 21] Is a directory`, and `[Errno 20] Not a directory: '…/file/out'` respectively, ran no test, and wrote no `results.json`. Under the revert each instead ended in a `FileNotFoundError`, `PermissionError`, `IsADirectoryError`, or `NotADirectoryError` traceback with exit 1, still running no test. The spec is read after `--out` is claimed, and a missing `--out` is created inside `claim_output` before its lock, so the error arises at two sites.

**Change.** `verify-mutation-runner.py` gains one case and extends one:

- `an_os_error_before_the_control_is_a_refusal` runs the runner with a missing spec, an unreadable spec, and an `--out` beneath a regular file, and asserts for each exit 2, stderr beginning with `error: `, the error's reason (`No such file or directory`, `Permission denied`, `Not a directory`) and the path it names, no traceback, no test run, and no `results.json`. The three errors are different `OSError` subtypes raised at both sites, so a handler narrowed to one subtype or moved to one site fails.
- `a_run_releases_its_output_however_it_ends_within_one_process` gains a run, `raised before the control`, whose `load_spec` raises an exception the runner does not expect; it must propagate out of `main` with the claim released, as the existing run inside the campaign already had to. The stand-in exception's message no longer says it was raised inside the campaign.

README's refusal sentence adds that a spec that cannot be read and a `DIR` that cannot be created are refused before building. `run-mutants.py` is unchanged. `./verify-mutation-runner.py` passes 117/117 on Python 3.13.9 and on `/usr/bin/python3` 3.9.6.

**Limitations.** The unreadable-spec variant relies on file permissions, so a verifier run as root, which reads a mode-000 file, would fail it, as it would the existing read-only write case. The diagnostic's reason text is macOS's `strerror` wording. An `OSError` before the control from other sources, such as `git` missing from `PATH`, an unreadable file while the copy is built, or an unreadable edit target, reaches the same handler but has no case of its own; the handler's breadth is held by the mutants above rather than by each source. An unexpected exception before the control still ends with a traceback and Python's exit 1, which README's exit codes did not describe; that was outside this boundary and is unchanged, and [NB45](NB45.md) later documented it.
