# NB63 — Nothing stops a SwiftUI `Picker` or `Slider` from returning to Sources

**Origin:** the NB62 analysis of 2026-11-14. On macOS 27 a SwiftUI `Picker` or `Slider` has no AppKit view, so hosted tests cannot see it. In particular, a voice picker reintroduced into the menu as a SwiftUI `Picker` would pass `MenuBarViewTests.testMenuNeitherShowsAVoiceControlNorFetchesTheCatalogItWouldNeed`, and since D31 no catalog fetch would reveal it. The main agent gave the user two ways to close the gap: a lint rule, or an accessibility-driven UI-test target, which would need its own isolation design.

**Decision:** D37 (2026-11-14). The user chose the lint rule.

## Implementation

**NB63 — Fixed (D37).** This is a configuration-only change, made directly by the main agent.

- `.swiftlint.yml` gains the strict custom rule `swiftui_self_drawn_control`.
  - `included` is `.*/Sources/.*\.swift`, the regex is `(?<![\w])(Picker|Slider)\b`, and comments, doc comments, and strings are excluded.
  - A comment beside the rule states its reason and its limits: type aliases and other self-drawn controls, such as a SwiftUI `Menu` used as a chooser.
- DESIGN's UI bullet names the rule.
- No source or test changed. `Sources/` named neither type outside comments.

### NB63 execution boundary (D37)

**Intent:** a strict SwiftLint custom rule fails every build that names SwiftUI's `Picker` or `Slider` type in `Sources/`, so pickers and sliders stay on D36's app-owned wrappers.

**Direction:**

- Add a rule `swiftui_self_drawn_control` to `.swiftlint.yml`, with `included` limited to `Sources/`, severity `error`, and comments, doc comments, and strings excluded like the existing rules.
- It matches the bare type names `Picker` and `Slider` not preceded by an identifier character, so `SwiftUI.Picker`, `Picker<…>`, `Picker.init`, and `Picker(` are all refused. `SuggestionPicker`, `MenuSlider`, `NSSlider`, `DragDeferringSlider`, `.pickerStyle`, and lower-case identifiers are not.
- A comment beside the rule states its reason and limits, as the existing rules do.
- DESIGN's UI bullet names the rule.

**Compatibility surface and non-goals:** build configuration only. No production or test behavior changes, and `Sources/` currently names neither type outside comments. Not in scope: other self-drawn SwiftUI controls (`Toggle`, `Menu`, `Stepper`, and the like); `Tests/`, which may host SwiftUI controls deliberately; and an accessibility-driven UI-test target, which D37 declined.

**Validation:**

- Full gates, which already run strict SwiftLint over `Sources` and `Tests`.
- Lint mutation evidence in scratch copies, with `swiftlint --strict` run against the candidate configuration:
  - (a) The rule refuses each spelling above: `Picker(`, `SwiftUI.Picker`, `Picker<`, `Slider(`, `Slider.init`.
  - (b) Revert: without the rule, the same file passes.
  - (c) Over-restriction: a file using every allowed name, plus `Picker` and `Slider` inside comments and strings, passes.
  - End to end, a scratch copy whose `MenuBarView` adds a SwiftUI voice `Picker` fails `xcodebuild` through the SwiftLint build phase, naming the rule.
