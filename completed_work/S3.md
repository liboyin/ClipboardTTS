# S3 — The mutation runner's output ownership is a scoped resource

**Origin:** a design proposal recorded on 2026-09-26 after [S2](S2.md)'s architecture discussion, with its structure validated by source inspection at `8c80839`: `claim_output` in `run-mutants.py` returned a raw file descriptor that `main` left open until the process exited. The CLI's lock lifetime was intentional, but acquisition and release were not a scoped resource that one process could exercise repeatedly. The user authorized it on 2026-09-27 (D22) as the first task of the mutation runner's sequence, ahead of [NB39](NB39.md), whose restoration case builds on the structure it leaves.

**Boundary:** `claim_output` becomes a context manager that takes the lock before anything in `--out` is deleted or written and releases it however its block ends, including on its own refusals after the lock was taken; `main` holds that scope from the claim through the campaign, each mutant's restoration, and the final `results.json` write. NB39, NB40, NB41, NB34, S4, and any change to verdicts, exit codes, diagnostics, deadlines, signal routing, or what `--out` accepts were out of scope. Validation was direct verifier cases on both interpreters, the unchanged live two-run case, mutation evidence against the unmodified verifier, AGENTS' gates, and the review skill's full procedure.

**Revalidation** at `3447012` on 2026-09-27, Python 3.13.9 and `/usr/bin/python3` 3.9.6, identically on both. A probe loaded `HEAD`'s runner from a verifier fixture repository and called its `main` twice in one process on the same `--out`: the first, refused after the claim with `--only nope`, exited 2 with `unknown mutants: nope`, and the second, a valid campaign, exited 2 with `--out … is in use by another run`, because the first run's descriptor was still open. A second `claim_output` beside a held one in the same process was refused the same way, since `flock` locks belong to open file descriptions, not processes. `claim_output`'s own symlinked-child refusal, which comes after the lock is taken, leaked its descriptor (one more open descriptor after the refusal), and the same process could not claim that directory again once the symlink was gone. The structure the entry describes therefore held.

**Change.** `claim_output` is a `contextlib.contextmanager`. After the existing directory and ownership checks it opens the marker, and one `try`/`finally` that closes the descriptor spans the non-blocking `flock`, the in-use refusal, the removal of the earlier `results.json`, the symlinked-child refusals, and the `yield`. Closing the descriptor releases the lock: it is the only descriptor on that open file description, and Python opens it non-inheritable, so no child holds it (probed on both interpreters: `get_inheritable` false, and no descriptor left after the block). `main` wraps everything after argument parsing in a `contextlib.ExitStack` and enters the claim at the point it was taken before, inside the existing pre-control `try`, so the refusals before and after the claim keep their `error:` diagnostics and exit 2, the signal handlers are installed where they were, and the campaign's `try`/`except`/`finally`, including the `results.json` write, runs inside the scope unchanged; leaving the block by a refusal, a return, or an exception releases the lock. An exception the runner does not catch still propagates with its traceback after `results.json` is written. The docstring, the comments at both sites, and README's sentence on the lock describe the scope.

**Verifier.** Two cases were added, and no existing case changed. `an_output_claim_is_released_however_it_ends` loads the runner in the verifier's own process: while a claim is held, a second claim is refused as in use; after a block that returns, after one that raises, and after a refusal of a symlinked `logs` child that is shown to follow the lock because it removed the earlier `results.json`, the same process claims the directory again, which is kept non-empty so that only the ownership marker allows it; and no descriptor is left open. `a_run_releases_its_output_however_it_ends_within_one_process` runs the fixture's runner five times in one child process on one `--out`: refused after the claim (`--only nope`, exit 2), failed in the campaign (a mutant whose generation fails, exit 2), raised in the campaign (`classify` replaced by one that raises an exception `main` does not catch), succeeded, and succeeded again, asserting after each that the process can claim the output again, and, through a `json.dumps` that probes the claim as each report is serialized, that all four runs that reached their report still held the output while writing it. Since a released claim is never retaken, holding it at the report shows it was held from the claim onwards, through every restoration. The live two-run case, `a_second_run_on_a_directory_in_use_is_refused`, is unchanged and still proves a concurrent run refused while the first run's control holds. `./verify-mutation-runner.py` passes 112/112 on Python 3.13.9 and on `/usr/bin/python3` 3.9.6; `HEAD`'s runner fails exactly the two new cases (110/112). Four further concurrent runs, two per interpreter, passed; they ran against the verifier before its last change, a comment, and each of the 22 mutation runs below against the final verifier also ran the whole suite, in which every case the table does not name for that mutant passed.

**Limitations.** The in-process case observes the lock at the moment each report is serialized, by replacing the runner's `json` with a probe, and at the end of each run; it does not probe between those points, and relies instead on a released claim never being retaken. A `main` that never leaves its claim is not a mutant this design can express within one frame's lifetime: CPython finalizes an unreferenced generator, closing its descriptor, when the frame that held it goes, so "missing cleanup" in `main` is represented by the revert, whose raw descriptor outlives `main`, and cleanup within `claim_output` by its own mutants. The descriptor count reads `/dev/fd`, which macOS provides; the verifier already assumes macOS.
