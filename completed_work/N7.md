# N7 — The automatic-playback prebuffer closure captures the manager explicitly

**Origin:** NB12's clean gate run on 2026-09-18 at `6578dac` (Xcode 27.0) reported `'weak' ownership of capture 'self' differs from implicitly-captured strong reference in outer scope [#ImplicitStrongCapture]` at `AudioPlayerManager.swift:275`. The inner `[weak self]` prebuffer action sat inside `scheduleAudio`'s `bufferQueue.async` closure, which captured `self` strongly without saying so. Selected on 2026-10-13 with NB17 under the grouped-task-execution workflow, as the first of that group's three commits.

**Boundary:** make the capture intent explicit so the warning resolves without suppression, and keep the deferred automatic start from retaining the manager across its delay. Only the audio-session contract (automatic playback after the first complete frame) was affected; menu, Settings, Services, clipboard, persistence and provider-request contracts were untouched. Non-goals: other capture-list cleanup, scheduler API changes, and NB17's test lifecycle work. Acceptance: no source warning at that site from a clean build with no diagnostic disabled; a test proving a held scheduled action does not keep a released manager alive; existing automatic-playback, generation-guard and B3 pause-revocation tests unchanged; revert, plausible-regression and over-restriction mutants each failing a named test.

**Revalidation:** the warning reproduced at `AudioPlayerManager.swift:275:98` in the clean baseline at `54dc35b`. No existing test held the prebuffer action past the manager's release.

**Fixed.** `scheduleAudio`'s audio-queue closure now names its capture, `bufferQueue.async { [self] in`, with a comment that the packet's processing holds the manager only until it runs while the deferred start captures it weakly. The inner action is unchanged. `testHeldAutomaticPlaybackActionDoesNotKeepReleasedManagerAlive` (`Tests/AudioPlayerManagerAutomaticPlaybackTests.swift`) holds the scheduled action with `ManualAutomaticPlaybackScheduler`, synchronizes with the audio queue through `changesAudioFormat(to:)`'s `bufferQueue.sync` and with the main queue, releases the manager, asserts it deallocated, and then runs the held action to show it does nothing.
