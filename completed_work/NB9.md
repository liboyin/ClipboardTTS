# NB9 — A format change cancels its paired request

Moved from [TODO.md](../TODO.md) on 2026-09-24 without rewording; the text below is the disposition as TODO recorded it, and its evidence is tied to the revisions it names.

**NB9 — Fixed.** A PCM format is applied through `SpeechSessionCoordinator.applyAudioFormat(sampleRate:)`, which cancels the request paired with the audio that change discards. The two halves were always one session: the buffered PCM and the request still delivering more of it were both decoded for the rate being replaced, so retiring the audio generation alone left that request streaming bytes the player was certain to drop — spending the provider call on speech nobody can hear, and holding `isStreaming` true so the menu went on offering to clear a buffer that was already empty. Each manager still revokes its own half, as when a session is replaced: the owner cancels the request and `setSampleRate` clears the audio, so one change advances each generation once. The request is released before the graph is touched, matching the order `cancel()` uses. The order is load-bearing: rebuilding the graph takes long enough for the request to complete inside it, and a cancellation arriving after that would find nothing to cancel and leave the finished request publishing the failure of a session the format change had already retired. `AudioPlayerManager.changesAudioFormat(to:)` answers whether a rate replaces the active format, and `setSampleRate` decides with that same answer, so the prediction and the change cannot disagree. `TTSNetworkManager.stopActiveSpeechRequest()` decides and revokes in one visit to `stateQueue` under callback authority, because a request completing between a separate check and the revocation would be "cancelled" by advancing a generation it no longer owned. Ownership is the context's own generation still being the current one: a fatally malformed Gemini stream advances the generation first and leaves its context in place until the revocation waiting at callback authority collects it, and cancelling that context would advance a generation nothing owns and swallow the no-playable-audio failure it was about to publish. Published `isStreaming` is not that decision either, since it stays true for the turn between a request releasing its context and its stop being published. Ownership now covers the one permitted retry: `processCompletedTask` keeps the completed attempt's context when that attempt earned a retry, so a format change arriving during the handoff cancels the logical request and `replaceActiveRequest`'s generation guard refuses the retry, where before it found nothing to cancel and let the retry stream into a session already torn down. Releasing ownership is still what a finished request does, and every generation move still clears or replaces the context, so a refused retry leaves nothing stale behind. Nothing else may: an unsupported rate applies no format, an unchanged one leaves the session speaking, and a change with nothing paired to it leaves that generation where it was, which is what a menu click waiting out its deferred clipboard read and a failure still on screen both depend on. `SettingsView` applies every rate through the owner rather than reaching past it to the player, so both routes that can replace a live format — the Custom sample-rate field and the synchronization every other edit runs — end the session they invalidate; each route has its own hosted test, because a revert on one alone leaves the other looking correct. Thirteen mutants were run against the committed state and each fails a named test: cancelling nothing, cancelling unconditionally, cancelling on every applied rate, splitting the revocation into two request-state visits, dropping the generation from the ownership test, dropping the ownership guard entirely, revoking without publishing the release, counting an unsupported rate as a change, inverting the format comparison, bypassing the owner from either Settings route, releasing ownership before the retry installs, and cancelling after the format is applied rather than before. The last three are the ones a window hides, and each is opened deliberately rather than waited for: `TTSNetworkManager` carries two observer seams that do nothing in production — one inside the revocation's request-state transaction, one between a retry's task being created and that retry owning the pipeline — and the audio graph's existing engine starter is the third, because a completion forced from it lands while the graph is being rebuilt. An invariant about what may interleave somewhere can only be stated from inside that somewhere. Cancelling after the application is not equivalent after all, as an earlier revision of this entry claimed: the rebuild takes long enough for the request to end inside it, and a cancellation arriving afterwards finds nothing to cancel and lets that request publish the failure of the session the change had already retired. README owns the current contract. NB10 still owns the rounding that decides whether opening Settings changes a fractional Custom rate at all, and therefore whether opening the window is itself such a change.
