# NB8 — Nested request-state publications apply in order

Moved from [TODO.md](../TODO.md) on 2026-09-24 without rewording; the text below is the disposition as TODO recorded it, and its evidence is tied to the revisions it names.

**NB8 — Fixed (D14).** Every request-state publication now goes through `publishRequestState` on the main queue. While one is being stored, a publication an observer triggers there, such as a Stop's clear and `isStreaming = false`, is queued unevaluated. The outer publication applies the queue in order right after its own store, before it returns. Each queued publication's generation check and message comparison therefore judge the state it replaces, and `objectWillChange` announces it after the outer value is stored. Revocation stays synchronous, and an observer-started request is still deferred to the next main-queue turn. The former publication-depth counter is now a flag, because a queued publication cannot nest. No production observer was shown to trigger the defect; SwiftUI observes after the store. `ReentrantPublicationTests` holds the state to D14 without draining the main queue. Fourteen mutants were run against four suites in an isolated scratch copy, with an unmutated control that passed. Thirteen each fail a named test: applying nested publications inline, either everywhere or in any one of the five publishing methods; deferring them to the next main-queue turn; applying the queue last-in first-out; never applying it; discarding nested publications; checking a failure's generation or the read-failure message when a publication is queued rather than when it applies; and deferring Stop's revocation along with its publications. The first review found that an inline migration warning survived. The migration regression and the check that a stale withdrawal announces nothing were added for it. Clearing the flag after the drain rather than before it survives and is equivalent. Between drained publications, nothing on the main queue reads the flag or notifies an observer, and each drained publication sets the flag around its own store. Off the main queue, only a concurrent request start reads it, and deferring that start to main or proceeding are both permitted. README owns the current behavior.
