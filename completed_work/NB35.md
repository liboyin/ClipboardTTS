# NB35 — Every tool run the mutation runner starts has a deadline

**Origin:** reported by [S2](S2.md)'s review on 2026-09-25 with a real hang run, and recorded in TODO as not independently validated: `run-mutants.py` started `xcodebuild test` with no bound, so a mutant that deadlocked the test run blocked the runner until it was interrupted, which ended the campaign with exit 2 and no verdict for that mutant. [NB33](NB33.md) then moved XcodeGen and `uname` into sessions of their own, so a terminal's Ctrl-C stopped neither of them if it hung, and left bounding that to NB35. The user assigned NB35 on 2026-09-26, after [NB38](NB38.md) and NB33.

**Boundary:** a runner-side deadline on each `xcodebuild test` run, build included: SIGTERM when it expires, SIGKILL if the tool has not exited within the short-tool deadline, and `NO-VERDICT` with a detail naming the deadline, so the mutant is unjudged and the campaign continues; a deadline on each shielded short tool, after which every process in its session is killed and the run stops with exit 2; `--test-deadline` to override the test-run default; and the deadlines recorded in `results.json`. NB34's reading of crashes and timeouts, a new verdict or exit code, S3's lock scope, S4's case selection, bounding the interrupt path's wait more tightly than the deadline, handling SIGHUP, and any change to signal routing were out of scope; `xcodebuild` stays in the runner's process group. Validation was verifier cases with stand-ins that hang until stopped, mutation evidence against the unmodified verifier, repeated runs for flakiness, real-Xcode runs, AGENTS' gates, and the review skill's full procedure.

**Revalidation** at `b8a8e2a` on 2026-09-26, Xcode 27.0. `HEAD`'s runner, run over this repository with `ClipboardTTSAppTests/ReentrantPublicationTests` selected and a production mutant that drains `queuedRequestStatePublications` without removing its head (`removeFirst()()` to `first!()`, an infinite loop on the main thread), read the control as `SURVIVED` and then stayed blocked: 300 s after the mutant's tests began its log had not changed for 296 s, the last line being `testAQueuedFailureThatAStopRevokedIsNeverAnnounced` started. A SIGINT to the runner ended it with exit 2, `interrupted by signal 2; the copy was restored`, no verdict, and nothing left running. A deadlock on a background queue does not reproduce the finding: replacing the callback-authority `NSRecursiveLock` with `NSLock` was `KILLED` over the whole bundle, because the tests' own expectation timeouts caught it. Three probes in a scratch copy with a test-level `DispatchSemaphore(value: 0).wait()` in `MockURLProtocolTests` showed what a bound must deal with. The test host runs with parent PID 1 in a session of its own, launched through launchd, so it is neither a descendant of `xcodebuild` nor in the runner's process group; SIGTERM to `xcodebuild` alone ended it at once with `** BUILD INTERRUPTED **` and no terminal marker, and SIGKILL to it alone, and the host and `xcodebuild`'s own children (`DTServiceHub`, `SWBBuildService`) were gone within one or two seconds either way. With `-test-timeouts-enabled YES -default-test-execution-time-allowance 60`, XCTest stopped the hung test after its one-minute minimum, restarted the host, ran the suite's other tests, and ended `** TEST FAILED **` (exit 65, 84 s); the log names the hung test only in `exceeded execution time allowance of 1 minute` and under `Failing tests:`, with no `error: -[…]` line, and `classify` read it as `FAILED-UNNAMED`.

**Decision within the boundary.** Xcode's test timeouts stay off. They bound a test, not a build, a host launch, or `xcodebuild` itself, and with them a hang would read as `FAILED-UNNAMED`, a judged verdict (exit 0) whose documented meaning, a finished failure naming no test, is NB34's open question; adopting that reading would have been a material choice. A runner-side deadline cuts the run short, which is what `NO-VERDICT` already covered ("no terminal marker … cut short"), with the exit code that already means a mutant got no verdict. A stopped run is `NO-VERDICT` whatever its log holds, because the deadline rather than the tests ended it; the only way its log could hold a terminal marker is an `xcodebuild` that printed one and then failed to exit. The detail names the deadline, so the outcome is not silent, and README's meaning of `NO-VERDICT` now includes a run its deadline stopped. The shielded tools are bounded too, because NB33 had made a hang in them impossible to interrupt from a terminal; their deadline stops the run as a failed tool does, rather than giving a verdict, since what the copy's generated project then holds is unknown.

**Allowance.** A full-bundle control from fresh derived data took about 50 s (1790406119 to 1790406169 in the revalidation run; 392 tests executed in 32.5 s), and the coverage gate's whole run 46 s. A mutant can legitimately make the tests' own waits expire and still end in a named kill: the `NSLock` mutant above took 95 s. The suite's explicit waits sum to about 577 s, 376 literal expectation timeouts totalling 408 s and 85 semaphore waits totalling 169 s, before teardown's per-test quiescence waits. The default of 1800 s covers that three times over; a slower selection can raise it with `--test-deadline`, which is also how a user tells a slow run from a hang. XcodeGen generates this project in about 30 ms (NB33's measurement) and `uname` answers at once, so the short tools get 60 s. The same 60 s is how long a stopped `xcodebuild` gets to exit before SIGKILL; on SIGTERM it exited at once.

**Change.** `run_tests` waits for `xcodebuild` with the test-run deadline; when it expires it calls `terminate()`, waits up to the short-tool deadline, then `kill()` and `wait()`, and returns `NO-VERDICT` with `the test run did not finish within N seconds and was stopped`. `xcodebuild` stays in the runner's process group, so NB33's routing of a terminal's signals is unchanged, and SIGTERM is what lets `xcodebuild` end the launchd-started host that the runner cannot reach by process group or parentage. `run_shielded` takes a deadline: it starts the tool with `Popen` in its own session, and on `TimeoutExpired` calls `kill_session` before reaping the tool, then raises a `RunnerError` naming the tool and the deadline. `kill_session` first SIGKILLs the tool's process group, so the tool itself dies and can be reaped even if nothing else works, then lists processes with `ps -A -o pid=` and SIGKILLs every one whose `getsid` is the tool's, repeating until a listing finds none, because a member can have left the tool's process group while staying in its session, and can fork while the processes are listed. Every listing shares one deadline, the short-tool deadline again, so a `ps` that hangs or fails, or members that keep appearing, end the attempt unconfirmed; the error then adds `not every process in its session could be confirmed stopped`, and the run stops with exit 2 either way. The tool is still unreaped, so no other session can have taken its id; macOS answers `getsid` for a zombie with ESRCH (probed), so the dead leader stops counting and the loop ends. An exited tool whose output something in yet another session keeps open leaves nothing to kill, and the stop still ends the wait. The pre-test generation, `uname`, and the post-restore regeneration all pass the short-tool deadline; the post-restore one raising inside the restoring `finally` stops the run, as NB33 made any failure there do. `--test-deadline SECONDS` (default 1800) is documented; `--tool-deadline` (default 60) is a hidden verifier seam like `--xcodebuild`. Both accept only a finite positive number. `results.json` gains `deadlines: {test_run, short_tool}`, because README promises that the file alone identifies its evidence and the test deadline can now decide whether a mutant gets a verdict. The module docstring and README describe the deadlines, the recovery, and why Xcode's timeouts stay off.

**Limitations.** A deadline is a clock: a test run that is merely slow past 30 minutes reads as `NO-VERDICT`, never as a false verdict, and its detail says to look; the verifier's timing cases rely on stand-ins finishing well inside a couple of seconds, which 24 loaded runs upheld. The runner does not itself verify that the test host has exited: it relies on `xcodebuild`, on SIGTERM or on dying, and Xcode's testing services to end a host launchd started outside its process tree, which the probes and both real runs observed through process listings rather than a case. A SIGKILL escalation leaves `xcodebuild`'s own children to exit on their own, as they did in the probe. A signal to the runner still waits for the test tool without a shorter grace; the test-run deadline now bounds that wait. A short tool that starts something in a session of its own escapes the session kill, as the output-holder case's holder does. The session kill relies on `ps` and `getsid`; when a listing cannot finish in time it says so rather than claiming the session empty, and between a member's `getsid` and its `kill` the member could exit and its pid be reused, which macOS's sequential pid allocation makes implausible within that window but nothing rules out. The hanging mutant in the real run was selected with one suite; the whole bundle's control duration was measured, but no whole-bundle hang was run.
