# NB46 — The startup refusal test establishes quiescence after its bounded wait

**Origin:** finding 1 of the main agent's read-only gap review of the [NB31](NB31.md)/[NB18](NB18.md) group on 2026-10-12; the user asked on 2026-10-13 to act on it. Executed together with NB47, one task per commit. NB31's `assertRefusesLoopbackRequestLocally` sent a real request to `http://127.0.0.1:9` and waited up to 2 s for its completion, but nothing established that the completion had run once that wait ended. README requires a test that calls code answering on another queue to own that queue and establish quiescence unconditionally after its bounded wait, and `AppStartupDependenciesTests` is a plain `XCTestCase` outside the mock-network scope's accounting. After a timeout, the completion could still write the outcome the assertions read, or fulfil an expectation whose wait had ended.

**Boundary:** whatever the wait's outcome, the helper knows its completion has run, or can no longer act on test state, before it asserts and returns. It must not change what NB31 proves: the request still carries the graph's own routing to the loopback literal, and the refusal's code and description are still asserted. Test-only. Non-goals: NB47, other suites, and NB31's assertions. Acceptance: the step is unconditional; a controlled probe shows the guarantee when the wait expires; NB31's refusal mutants still die; a revert of the step fails the probe.

**Change:** `Tests/QuiescentRequest.swift` adds `XCTestCase.completionError(of:configuration:description:timeout:)`. It builds a session of its own from the caller's configuration, with an owned serial delegate queue; only a session's creator chooses the queue its completion runs on. After the bounded wait it calls `invalidateAndCancel()`. A `sync` barrier on that queue then waits out a completion already running and closes a gate. A completion delivered later finds the gate closed, and neither writes the outcome nor fulfils the expectation. `assertRefusesLoopbackRequestLocally` now sends its request through that helper with `manager.session.configuration`, the configuration the manager's session was built from, which carries the graph's routing. Its assertions are unchanged.

The suite stays at 394 lines. Inline, the helper took it to 413 lines, past the 400-line limit, so it lives in its own file as one responsibility: owning a request's completion lifetime.

**Trade-off:** the refusal is now proven through a session built from the manager session's own configuration rather than through that session object. The refusal happens inside the protocol the configuration installs, before any response could reach the manager's delegate. The branch-header and first-protocol `canInit` assertions still read the manager's session directly. The reviewer judged this acceptable.

**URLSession behaviour verified:** a standalone probe on this machine ran 40 rounds of five scenarios, all against the loopback literal. Every one of the 200 completions ran on the owned queue. In all 40 expired waits, the cancellation completion arrived after a barrier issued immediately after `invalidateAndCancel()`, which is why the gate exists. A completion always preceded `didBecomeInvalidWithError` in 200/200 cases, but the design does not rely on that.
