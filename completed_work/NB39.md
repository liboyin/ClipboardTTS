# NB39 — A mutant whose edits cannot all be written leaves the copy restored

**Origin:** reported by [S2](S2.md)'s sixth review on 2026-09-25 and recorded in TODO as not independently validated: `run-mutants.py` writes a mutant's planned texts inside the `try` whose `finally` restores them, but moving `apply_plan` in front of that `try` survived the verifier, so a write failing partway through a multi-file mutant could leave earlier files mutated in the copy README says remains for inspection. The user authorized it on 2026-09-27 (D22) as the second task of the mutation runner's sequence, after [S3](S3.md).

**Boundary:** hold, with a verifier case, that a mutant whose edits cannot all be written leaves no file of the copy mutated, and pin what such a run reports today. The change was verifier-only, with a README clause; the runner stayed unchanged because revalidation found it already restored correctly. NB40, NB41, NB34, S4, and any change to verdicts, exit codes, diagnostics, or to what happens when a restore write itself fails were out of scope. Validation was the case on both interpreters, mutation evidence against the unmodified verifier, AGENTS' gates, and the review skill's full procedure.

**Revalidation** at `fda0cae` on 2026-09-27, identically on Python 3.13.9 and `/usr/bin/python3` 3.9.6. The moved-`apply_plan` mutant passed the 112-case verifier (112/112, exit 0) on both. A probe in the verifier's fixture ran a two-file mutant, `project.yml` then `Sources/Target.swift`, whose second write failed in two ways: the second target read-only, and the runner started with `RLIMIT_FSIZE` at 64 KiB and SIGXFSZ ignored, so the second write stored the bytes that fit and then failed with EFBIG, as on a full disk. `HEAD`'s runner restored both targets in both, and exited 2 after the control with `error: [Errno 13] Permission denied: <path>` or `error: [Errno 27] File too large`, no traceback, stdout holding only `control: SURVIVED`, the mutant unjudged and the next mutant not run, and a `results.json` with `complete: false`, `exit: 2`, that error, the control's `SURVIVED`, and no mutants. Under the moved-`apply_plan` mutant the same runs reported the same, but left `project.yml` as `SPEC_TWO`, and in the size-limit run left `Target.swift` truncated at 64 KiB of mutated text. Two observations were left as they are: the size-limit error names no file, because a failed write carries none; and in the read-only run the restore of the unwritable target fails again inside the `finally`, skipping the regeneration and the restoration check, which loses nothing because targets are restored in the order they were written and generation never ran for that mutant.

**Change.** `verify-mutation-runner.py` gains `a_mutant_whose_write_fails_partway_is_restored_and_stops_the_run`, which runs that two-file mutant beside a later mutant with each failure: the read-only target, and a 1 MiB file size limit against an edit of about 2 MiB. It asserts first that both targets in the copy are byte-identical to the repository's, then exit 2 with an `error: [Errno` diagnostic naming the failure, no traceback, stdout of only the control's line, only the control tested, `Generated.txt` as the control left it, and a `results.json` that is incomplete with exit 2, no mutants, the failure in its error, and the control `SURVIVED`. `run_runner` gains `file_size_limit`, which sets the runner's `RLIMIT_FSIZE` and ignores SIGXFSZ before it starts. README's sentence on restoration adds that a write of a mutant's edits that fails, such as to a read-only file or a full disk, stops the run with exit 2 and no verdict once the files it had written, even partly, are restored. `run-mutants.py` is unchanged. No existing case changed.

**Limitations.** The case relies on the spec's edit order for the earlier target being written first; the mutants show it is not vacuous today, but it does not observe the copy during the run. A full disk is represented by `RLIMIT_FSIZE`, which fails a write the same way, with EFBIG after the bytes that fit, rather than ENOSPC. The read-only failure assumes the verifier does not run as root. A restore write that itself fails, which the read-only run meets for a target that was never changed, is neither handled nor tested beyond that: the runner stops restoring at the first such failure.
