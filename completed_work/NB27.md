# NB27 — A later malformed Gemini inline part discards audio already validated ahead of it

**Origin:** source inspection after `912bf09`, which made `audioPayload(in:)` read every part of a candidate. Any part whose `inlineData` is unreadable or declares a non-audio media type makes the whole candidate `.invalid` and takes the fatal revocation path, so audio parts validated earlier in the same event are dropped. Before `912bf09` the first audio part returned immediately and a later part was never read. The risk recorded was that if Google added one non-audio inline part to an `AUDIO`-modality response, an utterance that previously played would go silent.

**Boundary:** decide from provider evidence whether an unplayable part accompanying valid audio is a corrupt stream or an ignorable extra, keeping the current rule until that evidence exists. Acceptance: the chosen rule and its evidence are stated in README, and both a malformed-only event and a mixed valid/malformed event keep a test.

**Accepted without change (user decision, 2026-11-02).** Evidence: on 2026-11-02 a Python client sent the app's own request body (`responseModalities: ["AUDIO"]`, prebuilt voice `Aoede`) to `:streamGenerateContent?alt=sse` for two 900-character prose passages on each supported model, `gemini-3.8-flash-lite-tts` and `gemini-3.8-flash-tts`, recording every part of every event. Across the four streams and 2,914 events, no event carried more than one part. Every `inlineData` part declared `audio/l16; rate=24000; channels=1`, each stream had exactly one `text` part (which the app skips, because it carries no `inlineData`), and every stream ended `STOP`. A mixed valid/malformed event, the only case where the rule discards valid audio, therefore did not occur; and in a one-part-per-event stream the whole-event rule and a part-by-part rule give the same result. The rule stays because a part that declares something else is more plausibly a corrupt or changed stream than an ignorable extra, and failing loudly keeps that visible.

**Tests:** both cases the acceptance names already exist in `Tests/TTSNetworkManagerGeminiStreamingTests.swift`. `testGeminiMalformedLaterAudioPartRevokesTheWholeEvent` covers the mixed event, and `testGeminiMalformedEventPublishesProviderAudioFailureWithoutDelivery` the malformed-only one. No code or test changed, so no gates, mutation runs or review were needed (AGENTS' documentation-only exemption). The baseline at `b6a86dc` passed `./check-coverage.sh` with 439 tests.

**Limitations:** four streams of short prose, on one day. A different voice, a much longer utterance, or a future model could stream several parts per event.

**Revisit if** a Gemini TTS response is seen with more than one part in an event, or with an `inlineData` part declaring anything other than 16-bit PCM.

**Cleanup:** the probe script and its output lived in the session scratchpad, outside the repository, and were deleted with it.
