# NB12 — Startup uses the key the launch migration secured

Moved from [TODO.md](../TODO.md) on 2026-09-24 without rewording; the text below is the disposition as TODO recorded it, and its evidence is tied to the revisions it names.

**NB12 — Fixed.** `APIKeyStartupState.load` now takes the selected provider's key from what the launch migration secured, and reads the store only when the migration secured nothing for that provider, which is how Settings' migration retry already adopts `securedSecrets`. A key moved out of plaintext therefore stays usable even when a second read would fail. Keychain-over-legacy precedence stays with the migration. Pending-migration guidance still outranks the startup read failure, and a launch with nothing to migrate reads and reports as before. The regressions use `ScriptedSecretStore` to refuse the read-back, and the two composed-startup tests now expect the injected store to see only the migration's read and save. Six mutants were run in an isolated scratch copy, and each fails a named test: reverting to the second read, adopting the first secured provider rather than the selected one, preferring a fresh read over the secured value, dropping another provider's pending guidance, never reading when nothing was secured, and dropping the startup read-failure message. README owns the current behavior. NB13 later gave Settings' own reads a retry.
