# NB43 — The runner reads test logs in the locale's encoding

**Group:** NB43 and NB28 were executed as one group on 2026-10-27 because NB28's evidence runs through the runner NB43 corrects. They were committed separately, NB43 first, each with its own validation and review. The working record, specs, logs and reviews are retained outside the repository at `/Users/liboyin/Code/ClipboardTTS-NB43-NB28-review/`.

**Origin:** NB40's investigation on 2026-09-28 found that `run-mutants.py` decoded its spec, edit targets and tool stderr as UTF-8 but read test logs with `read_text(errors="replace")`, in the locale's encoding. Under `en_US.ISO8859-1` a non-ASCII test name was garbled in `KILLED` details, `results.json` and the selector check. The verifier was also locale-dependent there: with Python 3.13.9 under `en_US.ISO8859-1` it passed 110/110 at `916f254` and 113/113 at `c100ba0`, but only 51/116 at `2500350`, and the cause had not been diagnosed.

**Revalidation at `5bcfe49`:** the three log reads (verdict, control's selector check, a surviving mutant's selector check) were unchanged. With Python 3.13.9 the verifier passed 154/154 under `en_US.UTF-8` and 87/154 under `en_US.ISO8859-1`, mostly with the stand-in control read as unjudged. Revalidation also found a consequence the entry did not name. The runner prints verdict details to stdout, whose encoding is strict under ISO 8859-1. Once logs decode as UTF-8, a name outside Latin-1, or a U+FFFD from NB40's decoding, would raise there.

**Boundary:**

- Read every test log as UTF-8 whatever the locale, keeping NB40's U+FFFD replacement.
- Keep the stdout verdict line from raising on a name the locale cannot encode, while `results.json` keeps the exact name.
- Diagnose the verifier's locale dependence and fix it where it lives.
- Non-goals: other decoding sites, classification, exit codes, deadlines, signals, copying, locking, the tools' environment, and Swift code.
- Validation: the full verifier under UTF-8, ISO 8859-1 and `C` on Python 3.13.9 and 3.9.6, a new case run under a non-UTF-8 locale, and mutation evidence against the verifier.

**Superseding user decisions (2026-10-27, after review round 1):**

- Fix both Non-blocking review findings in this change.
- Fold in the implementation agent's US-ASCII observation. This extends the boundary: the verifier must also pass under `en_US.US-ASCII`, and under `PYTHONIOENCODING=utf-8`.

**Diagnosis:** `write_stand_in` wrote every stand-in in the locale's encoding. Since NB40 (`2500350`), the stand-in test tool's source holds `ÉtéSuite`. Under ISO 8859-1 that is written as Latin-1, and Python reads a script's source as UTF-8, so the stand-in stopped with a `SyntaxError` before it ran. The control then had no verdict. Changing only that write took `5bcfe49`'s verifier from 87/154 to 152/154 under ISO 8859-1. The remaining two failures were NB43's runner defect itself and a case expecting a literal U+FFFD on a stderr that escapes it under Latin-1.

**Change:**

- **`run-mutants.py`:**
  - `read_log` reads each test log as UTF-8 with replacement, at all three sites.
  - The `__main__` block sets stdout to `backslashreplace`, so a verdict line escapes what the locale cannot carry. Output under UTF-8 is unchanged, and `results.json`, written as ASCII JSON, keeps the exact name.
- **`verify-mutation-runner.py`:**
  - Stand-ins are written as UTF-8. The stand-in test tool reads its target as UTF-8 and writes its record with `ascii()`.
  - The runner and other non-ASCII files are copied, rewritten and parsed as bytes.
  - NB40's two cases compare through `as_printed`, which matches the locale's escaping.
  - The verifier's own report escapes what its stdout cannot carry.
  - The new case `a_test_name_outside_the_locale_s_encoding_is_matched_and_reported_exactly` runs the runner under ISO 8859-1 and `PYTHONIOENCODING=iso8859-1:strict`, whatever the verifier's own environment. It selects a suite named with `Ω` and asserts the exact escaped verdict lines, the UTF-8 log bytes, the exact `KILLED` details in `results.json`, and that both selector checks match.
- **README:** the runner's verdict paragraph states the UTF-8 log reading and the escaped verdict line.
- **[NB40](NB40.md):** gains a line linking this record for its locale limitation.

**Limitations:**

- `as_printed` assumes that the runner and the verifier share one output encoding. A non-UTF-8 locale combined with a `PYTHONIOENCODING` that names a different encoding would still fail NB40's two cases. That combination was not tested or addressed.
- Two pre-existing deadline cases (`a_short_tool_past_its_deadline_is_killed_with_its_session_and_stops_the_run` and `a_short_tool_whose_output_outlives_it_is_stopped_at_its_deadline`) failed only when the implementation agent ran three verifier configurations alongside mutant runs. They passed in isolation and in every other run. The suspected cause, load against the fixtures' 2-second tool deadline, is a hypothesis that has not been demonstrated, and it is unrelated to this change.
- No real `xcodebuild` log under a non-UTF-8 locale was exercised. The new case uses the stand-in tool.
